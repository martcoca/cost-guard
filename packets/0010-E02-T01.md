## Context

You built this action and you released it. T05 then demonstrated its one real weakness:
adding `google_compute_router_nat` to the denylist required a pin bump in all three
consumers before any of them enforced it. Your own evidence put it plainly —

> A denial is in force in a repository when, and only when, someone opens a pull request
> there. Until then that repository allows what the portfolio has denied, silently and with
> a green check.

This packet makes that state **loud** rather than silent. It does not fix the bump; it
removes the silence.

## The tension to resolve, and it is the interesting part

The guard's most valuable property is that **it needs nothing**. It reads a plan file and
exits 0, 1 or 2 with no network, no credentials and no service. Freshness, by contrast, can
only be known by asking what the current release is.

**The guard's verdict must not acquire a network dependency.** A denied resource is denied
whether or not GitHub is reachable. Whatever you build, a network failure must never turn a
`1` into a `0`, and must never turn a clean plan into a failure either — that would make
every consumer's CI depend on an API call it does not need.

So freshness is a **separate signal** from the verdict. How you carry it is yours to decide:
a distinct output, a warning annotation, a separate step, a separate action. Weigh at least
these and say why you rejected the ones you rejected:

- **Inside the action**, as an extra output plus a workflow annotation.
- **A second composite action** consumers add next to the guard.
- **Neither** — because a platform feature already does it. Dependabot's `github-actions`
  ecosystem opens a pull request when a new release exists, and combined with auto-merge
  that is the *bump*, not just the warning. **Check this properly before building
  anything.** If it solves the problem, the honest deliverable is that finding plus the
  configuration, and it is worth more than a mechanism you wrote.

## Goal

A consumer pinned behind the current release is told so by its own CI, without the guard's
verdict depending on the network.

## Boundary

**This repository only.** Do not modify `platform-aws`, `platform-gcp` or `platform-azure` —
adopting this is T02.

Do not change the denylist, the guard's behaviour, or the exit contract 1/0/2.

Do not build automated pin bumping that requires a token. Cross-repository write authority
is not yours, and if the answer needs one, stop and say so.

No release, no tag, unless the packet's Check requires demonstrating one — and if it does,
that is publication, which is not yours. Stop and say so.

## Done when

- **A consumer can learn it is behind**, by a mechanism documented in the README.
- **The guard's verdict is unchanged and network-independent.** Prove it: run the guard with
  no network at all and show 1/0/2 still behave exactly as before.
- **Unknown freshness is reported as unknown**, never as fresh. If the current release
  cannot be determined, the signal says so.
- **A network failure cannot change a verdict.** Show a denied plan still exiting 1 when the
  freshness lookup fails.
- **The comparison is between real versions**, not a string equality that a moving tag
  defeats. A consumer on `@v1` and a consumer on `@v1.0.0` are in different situations and
  the mechanism must not confuse them — your own T05 evidence traced exactly this.
- If the conclusion is that Dependabot already solves it: **a working configuration**, a
  demonstration that it detects a new release, and an honest statement of what it does not
  cover.
- Every rule above has a test that can fail, and the suite still proves the exit contract.

## Check

From the repository root:

```bash
scripts/test-cost-guard.sh
scripts/test-suite-can-fail.sh
```

Then demonstrate, with output in the pull request:

1. **The guard with no network**: denied → 1, clean → 0, undecidable → 2. Unchanged.
2. **A consumer pinned to an older release** is reported as behind.
3. **A consumer pinned to the current release** is reported as current.
4. **Freshness lookup failing** — show the verdict is still correct and the freshness signal
   says "unknown" rather than "current".
5. If you chose Dependabot: show it opening or proposing the bump, and state plainly what
   happens between the release and someone merging that pull request. **That window is the
   residual risk and it does not disappear.**

## Notes

true; a configuration file and a clear explanation beat a hand-built checker.

The window between a release and a consumer picking it up cannot be closed by detection
alone. Name its size in the evidence. Someone will eventually need an emergency denial and
will want to know how long it takes to be real.
