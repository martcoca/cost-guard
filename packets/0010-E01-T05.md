## Context

This initiative exists because one denylist lived as three byte-identical copies and
keeping them identical had already meant hand-merging the same change twice.

T01 extracted the guard. T02, T03 and T04 cut the three platform repositories over to the
released action. **Every one of those could pass while the promise remains untested**, and
it currently is: nothing has yet demonstrated that a single change to the denylist reaches
all three consumers. Three repositories consuming the same action is a *plausible* claim
about propagation, not a demonstrated one.

That demonstration is this packet, and it is the only one whose failure would mean the
initiative did not deliver what it set out to.

The moving tag is the mechanism under test. Consumers pin `@v1.0.0` today; a new denied
type ships as `v1.0.1` with `v1` moved to it. Whether a consumer picks the change up
therefore depends on **how it pinned**, and that is exactly the thing worth learning before
someone needs an emergency denial.

## Goal

A denied type added once in this repository is demonstrably enforced by all three platform
repositories, and the mechanism by which they pick it up is written down rather than
assumed.

## Boundary

**No cloud mutation anywhere.** No `tofu apply`, no provisioning, no IAM change. Plan-time
evidence only.

**Do not change what is denied in a way that outlives this packet** unless the type is one
the portfolio genuinely wants denied. Prefer a real addition if there is an obvious
candidate; otherwise use a clearly-labelled throwaway type and remove it before finishing.
Say which you did and why.

You may open pull requests in the platform repositories **only if** the propagation
mechanism genuinely requires it — for example if consumers pin an immutable tag and must be
bumped. If it does, that is itself the finding: propagation is not automatic, and the
initiative's premise needs qualifying rather than celebrating.

Do not modify the guard's behaviour or its exit contract.

## Done when

- **A denied type is added once**, here, in `cost-guard-denylist.json`.
- **A release carries it**: `v1.0.1` tagged, and `v1` moved to it. Tagging is publication;
  if you hold no authority to tag, stop and say so rather than working around it.
- **All three platform repositories are shown enforcing the new type** against a fixture
  plan that creates it — three runs, three refusals, linked.
- **The propagation path is written down**: for each repository, whether it picked the
  change up automatically or needed a pin bump, and how long that took.
- **The failure mode is named**: what happens to a consumer pinned to `@v1.0.0` when a
  denial ships. Is it silently un-protected? Nothing in this initiative currently answers
  that, and every future denial depends on the answer.
- **If propagation is not automatic**, the evidence says so plainly and proposes what would
  make it so. A partial result honestly reported closes this packet; a claim of propagation
  that rests on a manual bump does not.

## Check

From this repository:

```bash
scripts/test-cost-guard.sh          # still exits 0 with the new type present
scripts/cost-guard.sh tests/fixtures/<new-type-plan>.json; test $? -eq 1
```

Then the demonstration, which is the packet:

1. **Show the denylist change and the release** that carries it.
2. **For each of `platform-aws`, `platform-gcp`, `platform-azure`**: a CI run refusing a
   plan that creates the new type. Link all three.
3. **State, per repository, how it received the change** — moving tag, pin bump, or not at
   all.
4. **Show a consumer pinned to the previous immutable tag** and state whether it enforces
   the new denial. Whatever the answer, it is the most useful line in the evidence file.
5. **Restore the denylist** if you used a throwaway type, and show the three repositories
   back to their prior verdicts.

## Notes

The honest outcome here may be that propagation requires a pin bump in three repositories,
which is the hand-merge this initiative set out to end, relocated from a file to a version
string. **If that is what you find, say it.** T01's evidence already flagged the risk when
it weighed a digest-verified release fetch and noted the pin would need hand-updating in
three places.

That result would not mean the work was wasted — one implementation and one test suite is
still worth having — but it would mean the epic's Goal is not met as written, and the
epic should say so rather than the evidence being quietly softened.

Report what you could not verify. An honest gap is a result; a silent one is a defect.
