# 0010-E02-T01 — Report an out-of-date pin

**The Dependabot question first, because the packet asked for it first: no, it does not
solve this.** It addresses the *bump*, which this packet explicitly is not about, and it
cannot deliver the signal, because its output channel is the existence of a pull request
and its resting state is silence. On top of that it does not work on these three consumers
today, for two reasons I demonstrated rather than guessed.

So the deliverable is a **second composite action** — `freshness` — plus the Dependabot
finding and a template for T02 to adopt once the two blockers are cleared.

## Why Dependabot is not the answer

**1. Its resting state is silence, which is the defect.** Dependabot reports "you are
behind" by opening a pull request. It reports everything else — up to date, disabled,
misconfigured, rate-limited, schedule not yet fired, a lookup that failed — by doing
nothing. The epic is "a consumer cannot be silently behind", and a mechanism whose normal
output is silence cannot satisfy "unknown freshness is reported as unknown, never as
fresh". No pull request is indistinguishable from no problem. That is the same shape as the
green check T05 found, moved one level up.

**2. It would break all three consumers today.** Dependabot's `github-actions` ecosystem
updates `.github/workflows/*` and a root `action.yml`, and nothing else — GitHub's own
documentation: *"Dependabot will search the `/.github/workflows` directory, as well as the
`action.yml`/`action.yaml` file from the root directory."* Every consumer keeps its pin in
`config/cost-guard-action.txt`, and every consumer's `check-ci-contract.sh` asserts that
every `uses:` equals that file. I simulated a Dependabot-shaped bump — workflows only, no
other file — against a throwaway copy of each consumer at its current `main`:

```
=== platform-gcp after a Dependabot-shaped bump (workflows only) ===
  exit: 1
  Workflow uses martcoca/cost-guard@v1.0.2 but the pin in config/cost-guard-action.txt is martcoca/cost-guard@v1.0.1.
=== platform-aws after a Dependabot-shaped bump (workflows only) ===
  exit: 1
  Workflow uses martcoca/cost-guard@v1.0.2 but the pin in config/cost-guard-action.txt is martcoca/cost-guard@v1.0.1.
=== platform-azure after a Dependabot-shaped bump (workflows only) ===
  exit: 1
  Workflow uses martcoca/cost-guard@v1.0.2 but the pin in config/cost-guard-action.txt is martcoca/cost-guard@v1.0.1.
```

The pull request would go red and never auto-merge. And `platform-azure` has a second
blocker underneath the first — it checks the release out at `ref:` for its
denylist-agreement job, which is an input to `actions/checkout`, not a `uses:` ref, so
Dependabot will not update it either. With the pin file hypothetically solved:

```
=== platform-azure: even if Dependabot ALSO updated the pin file ===
  exit: 1
  Missing required contract text in .github/workflows/cost-guard.yml: ref: v1.0.2
```

Both are fixable and neither is Dependabot's fault — they are the cost of the pin-file
design, which is otherwise good and which I would not remove without a decision. They are
written down in `docs/dependabot-for-consumers.yml` so T02 does not rediscover them.

**3. Adopting it as-is would quietly reverse a decision this portfolio already made.**
These repositories merge on green with nobody reading the diff. Dependabot plus auto-merge
means what the guard denies can change in a consumer with no human involved — which is
exactly the property all three consumers chose immutable pins to prevent, each recording
that reasoning in its own evidence. That may well be what the portfolio wants now, but it
is a reversal and it should be made deliberately rather than arrive as a side effect of a
config file. **I did not enable Dependabot in this repository** for the same reason: it is
a standing rule with automatic-merge consequences, and that is the Founder's call, not
mine.

## What I built instead, and why it is a separate action

Options weighed, as the packet required:

- **Inside the guard action, as an extra output and an annotation. Rejected.** The guard's
  most valuable property is that it needs nothing. Sharing a step means the guard's process
  makes a network call on every run — latency and a new failure surface on the one step
  that must be dependable — and it entangles the two things a consumer must be able to tell
  apart. A consumer reading `steps.guard.outcome` would not know whether the failure was a
  denial or a lookup. Keeping them in one step also makes the forbidden coupling the *easy*
  future edit rather than a visible one.
- **A second composite action. Chosen.** `martcoca/cost-guard/freshness@<ref>`, a
  sub-action of the same repository, so it versions and ships with the guard and needs no
  new repository — which I could not create anyway. Different step, different process,
  different outcome. The guard cannot acquire a network dependency by accident, because the
  network lives somewhere else.
- **Neither, because Dependabot does it. Rejected**, for the three reasons above.

## The rules, and the test that can fail for each

| Rule | Test | Mutation that must turn it red |
|---|---|---|
| The verdict never touches the network | `test-no-network.sh` | a `curl` added to the guard |
| Unknown is never reported as current | `test-freshness.sh` | every `status=unknown` becomes `status=current` |
| Unknown never fails, even under `fail-on-stale` | `test-freshness.sh` | — asserted directly |
| The comparison is by version, not string | `test-freshness.sh` | — asserted directly, via `@v1` |
| The exit contract still holds | `test-cost-guard.sh` | denylist holed; empty-input path softened |

`scripts/test-suite-can-fail.sh` runs the mutations. All five:

```
PASS  the suite passes unmutated
PASS  aws_nat_gateway is removed from the denylist, and the suite failed
PASS  the empty-input path is softened to exit 0, and the suite failed
PASS  the guard is given a network call, and test-no-network.sh failed
PASS  an unknown lookup is reported as current, and test-freshness.sh failed
```

The network-call mutation is the one worth having. It changes no fixture's expected exit
code, and every other suite in this repository stays green with it applied — so without
this specific test, the guard could acquire a network dependency and nothing would notice.

**A defect I introduced and caught here, worth recording:** my first version of the
unknown-as-current mutation guarded itself with `grep -q 'status=current'`, a string
already in the file for another reason. The guard passed without the mutation applying, and
the meta-test cheerfully reported the suite as sound. A mutation check that passes without
mutating is worse than no check, because it certifies. It now asserts the word `unknown` is
gone from the file entirely.

## Check, as run

```
scripts/test-cost-guard.sh        exit 0
scripts/test-suite-can-fail.sh    exit 0
scripts/test-freshness.sh         exit 0
scripts/test-no-network.sh        exit 0
scripts/demo-consumer.sh          exit 0
```

### 1. The guard with no network — unchanged

`scripts/test-no-network.sh` proves this twice over. Statically, neither `cost-guard.sh`
nor `action-entrypoint.sh` contains a network primitive on any path. Dynamically, with the
network genuinely removed:

```
Dynamic: the exit contract with the network removed (sandbox)
PASS  isolation confirmed: a control request fails inside it
PASS  denied create                      exit 1
PASS  denied create (the new type)       exit 1
PASS  denied create (events)             exit 1
PASS  clean plan                         exit 0
PASS  errored plan                       exit 2
PASS  unrecognizable input               exit 2
PASS  empty input                        exit 2
```

Two things make this a proof rather than a gesture. It **verifies the isolation is real**
before trusting any result from inside it — a sandbox that silently allowed the network
would make every line above meaningless and green. And where no isolation mechanism exists,
it **fails** rather than passing on the static check alone: a proof that did not run is not
a proof, and quiet passes are the recurring defect in this organization.

### 2, 3 and 4. Behind, current, and unknown — against the live API

```
martcoca/cost-guard@v1.0.0                 status=behind   exit=1
martcoca/cost-guard@v1                     status=current  exit=0
martcoca/cost-guard@v1.0.1                 status=current  exit=0
martcoca/does-not-exist-cost-guard@v1.0.0  status=unknown  exit=0
```

All four with `fail-on-stale: true`. Read directly from the process, not through a pipe.

The second line is the one that needed care. `@v1` and `@v1.0.1` are different strings and
the same commit; a string comparison would report every consumer on the moving tag as
permanently behind. Both refs are resolved to commits and the commits compared, so `@v1`,
`@v1.0.1`, and a raw SHA of that commit all read `current`. T05 traced exactly this
confusion, which is why the packet asked for it.

The fourth line is the packet's item 4, and the verdict alongside it:

```
freshness exit: 0   status=unknown
  cost-guard freshness: unknown — the current release could not be determined

  --- and the guard, in the same conditions:
  guard exit: 1 (denied plan, no network at all)
  guard exit: 0 (clean plan, no network at all)
```

The lookup failed, said so, did not fail the step even though asked to fail on staleness,
and the verdict was untouched.

## The window, named

Detection does not shorten the window between a release and a consumer enforcing it. It
only stops the window being invisible.

- **Before this packet:** unbounded, and unobservable. Nothing anywhere reported a stale
  pin. T05 had to write a fixture specifically to catch it.
- **After this packet, with the action wired into a consumer's plan workflow:** still
  unbounded, but observable on **that consumer's next CI run**. Which for
  `platform-aws` is every pull request and every push to `main`, and for `platform-gcp` and
  `platform-azure` likewise on their `cost-guard.yml`. So: hours to days in normal traffic,
  and *never* on a repository nobody pushes to — which is precisely the repository most
  likely to drift.
- **With `fail-on-stale: true`:** the window becomes "until someone needs CI to pass",
  which is the shortest this can get without automated bumping.

**Someone will eventually need an emergency denial.** The honest number for "how long until
it is real everywhere" is still *however long it takes three humans to open three pull
requests*, and nothing in this packet changes that. A scheduled run of the freshness action
in each consumer would put a floor under the detection half — a daily job that goes red
while behind — and I would recommend it in T02 over relying on incidental pushes.

## What T02 needs to adopt this

1. **One step per consumer**, next to the existing guard step:
   ```yaml
   - uses: martcoca/cost-guard/freshness@<pin>
     if: always()
     with:
       pin: martcoca/cost-guard@<pin>
   ```
   `if: always()` matters — a denied plan fails the guard step, and that is exactly when
   knowing the pin is stale is most useful.
2. **Decide `fail-on-stale` per repository.** Default `false` reports and does not block.
   `true` makes a release red every consumer's CI until bumped, including pull requests
   with nothing to do with the guard. My recommendation: `false` on pull requests, `true`
   on a scheduled job, so staleness blocks nobody's unrelated work but cannot be ignored
   indefinitely.
3. **Feed it the pin file, not a literal.** Each consumer already has
   `config/cost-guard-action.txt` as the single source of the pin, and each contract check
   already asserts every `uses:` equals it. Reading the same file into `pin:` keeps that
   property; hardcoding the string into the freshness step adds a fourth place to update.
4. **Extend each `check-ci-contract.sh`** so the freshness step cannot be deleted or
   excused, the same way the guard step cannot be. Otherwise this is a check that can be
   removed without anything going red — the defect `platform-gcp` found in its own contract
   script during T04.
5. **The two Dependabot blockers** in `docs/dependabot-for-consumers.yml`, if the portfolio
   wants the bump automated as well as the staleness reported.

## What I could not verify

- **That Dependabot opens the bump pull request.** I did not enable it anywhere, so the
  detection half is documented and reasoned, not observed. What *is* demonstrated is the
  consequence — that its pull request would fail all three consumers' contract checks —
  which is the part that decides whether it is usable. Whether it bumps a `@v1`-style pin
  on a patch release is also unresolved: the GitHub documentation I read does not state it
  either way, and I did not want to assert it from memory. It does not affect this
  packet's design, because the freshness action resolves `@v1` correctly regardless.
- ~~**The freshness action on a real runner.**~~ **Closed.** This paragraph originally
  recorded it as unverified. All five checks passed at `fcdf836`, and the runner facts are
  now observed rather than reasoned:

  ```
  cost-guard freshness: behind — pinned to v1.0.0 (83999e6); the current release is v1.0.1 (93fada3)
  ##[warning]pinned to v1.0.0 (83999e6); the current release is v1.0.1 (93fada3)
  cost-guard freshness: current — v1 and v1.0.1 are the same commit (93fada3)
  cost-guard freshness: unknown — the current release could not be determined
  pinned to v1.0.0: behind
  pinned to the moved v1: current
  ```

  The sub-action resolved, its inputs and outputs bound, and the warning annotation
  rendered. `$GITHUB_ACTION_PATH/../scripts/freshness.sh` therefore resolves as designed —
  that was a separate gap in the original file and it is closed by the same run.

- **The Linux isolation fallback was needed, and worked.** Worth recording because the
  concern was real: Ubuntu 24.04 restricts unprivileged user namespaces, so `unshare -rn`
  is not dependable on a runner. The probe fell through to the third candidate and said so:

  ```
  Dynamic: the exit contract with the network removed (sudo-unshare)
  PASS  isolation confirmed: a control request fails inside it
  ```

  The no-network proof is therefore real on Linux CI, not only on the authoring Mac. Had
  the detection been written to assume a mechanism rather than probe each one, this job
  would have failed on the runner — or worse, been written to skip, and passed without
  proving anything.
- **Behaviour under API rate limiting specifically.** I tested an unreachable repository
  and a missing ref, both of which take the same code path as a rate-limited response —
  `gh` exits non-zero and the status is `unknown`. I did not induce a real 403.
- **No cloud call, no cloud mutation, nothing applied.** No tag, no release, no
  modification to any platform repository. The three consumers were read and copied to
  throwaway directories; `git status` in each is unchanged.
