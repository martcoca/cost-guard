# 0010-E01-T05 — One change, three clouds

**The headline: propagation is not automatic.** A denylist change made here does not reach
any of the three platform repositories on its own. All three pin `@v1.0.0`, an immutable
tag, so a new release is invisible to them until each repository bumps its pin. That is
three pull requests for one denial — the hand-merge this initiative set out to end,
relocated from a file to a version string, exactly as this packet's Notes anticipated.

The rest of this file is what that claim rests on, and what it does and does not mean.

## The change

`google_compute_router_nat` — GCP Cloud NAT — added to `cost-guard-denylist.json` at
`~$32/mo`.

**This is a real addition, not a throwaway, and it outlives the packet.** The Boundary
preferred a real one if there was an obvious candidate, and there was: NAT was denied on
two clouds of three. `aws_nat_gateway` and `azurerm_nat_gateway` were both on the list;
GCP's equivalent was not, while `google_compute_forwarding_rule`,
`google_container_cluster`, `google_compute_instance` and `google_sql_database_instance`
were. Cloud NAT is billed the way the other two are. The asymmetry looks like an omission
rather than a decision, and closing it is worth more than a fake type that gets deleted
again. The Founder confirmed keeping it.

Checked before proposing it:

- Nothing in `platform-gcp`'s OpenTofu creates a `google_compute_router_nat`, so the new
  denial does not break that repository's real plan.
- `platform-azure`'s `check-denylist-agreement.sh`, the one downstream check that reads
  this file, stays green: it compares `azurerm_*` types against Azure Policy in one
  direction and Policy's `tofu_types` against the guard in the other, and a `google_*`
  type is outside both. Run against the new denylist directly:
  `Denylists agree (guard denylist from COST_GUARD_DENYLIST=…)`, exit 0.

The file grew from 30 entries to 31. The diff is five inserted lines and no other change.

## The failure mode, which is the most useful thing here

`scripts/probe-propagation.sh` materializes a ref the way `uses: owner/repo@<ref>` does and
runs the action's own entrypoint against a plan. Against a plan that creates the newly
denied type:

```
Plan under test: tests/fixtures/plan-with-gcp-nat.json
Creates:         google_compute_router_nat

REF            COMMIT     VERDICT      DENYLIST HAS IT
-------------- ---------- ------------ ---------------
v1.0.0         83999e6    allow (0)    no
v1             83999e6    allow (0)    no
HEAD           5276cb3    deny (1)     yes
```

**A consumer pinned to `@v1.0.0` when a denial ships is silently un-protected.** Not
broken, not warned, not failing — it exits `0`, its CI goes green, and it creates the
resource the portfolio just decided to deny. There is no signal anywhere that it is
enforcing a frozen list. From outside, "up to date with nothing to deny" and "a year
behind" are the same green check.

That the `allow` is specifically about the new type, and not a broken extraction, is shown
by running the same probe against a type `v1.0.0` already knew:

```
Plan under test: tests/fixtures/plan-with-nat.json
Creates:         aws_nat_gateway

REF            COMMIT     VERDICT      DENYLIST HAS IT
-------------- ---------- ------------ ---------------
v1.0.0         83999e6    deny (1)     yes
HEAD           5276cb3    deny (1)     yes
```

## Why all three are pinned this way — it was deliberate

This is not an oversight to be corrected quietly. T02, T03 and T04 each chose `@v1.0.0`
over `@v1` independently, and each recorded the same reasoning in its evidence file:

> The moving tag would let what is denied change here with no commit in this repository,
> which is the thing the Boundary's "do not change what is denied" protects. A denylist
> update should be a deliberate one-line bump of `config/cost-guard-action.txt`.

That argument is sound. An immutable pin is the supply-chain-safe choice, and each
repository built real machinery on it — `config/cost-guard-action.txt` as the single source
of the pin, with `check-ci-contract.sh` asserting every `uses:` in every workflow equals it.

**But it trades propagation away, and nothing recorded the trade.** Each packet weighed the
pin as a supply-chain decision. None of them weighed it as a propagation decision, because
none of them was the packet that shipped a second denial. The cost of the choice only
became visible here.

## What one denial actually costs

Per repository, a bump touches `config/cost-guard-action.txt` and every `uses:` in the
workflows — the contract check requires them to agree, so they move together:

| Repository | Pin file | `uses:` occurrences | Files changed |
|---|---|---|---|
| `platform-aws` | `martcoca/cost-guard@v1.0.0` | 7 | 3 |
| `platform-gcp` | `martcoca/cost-guard@v1.0.0` | 7 | 3 |
| `platform-azure` | `martcoca/cost-guard@v1.0.0` | 7 | 3 |

So: one denylist edit here, then **three pull requests, nine files, twenty-one occurrences**
before the denial is in force everywhere.

**It is not as bad as what it replaced, and the difference is worth stating precisely.**
The original problem was hand-merging denylist *content* into three repositories, where a
typo or a missed entry meant three lists that silently disagreed about what was denied.
That cannot happen now: each consumer runs one exact released version, the contract check
forbids the pin and the workflows drifting apart, and a repository is never *partially*
updated. What survives is the **cadence** problem — one decision still needs three
repositories to act before it takes effect, and until they all do, the portfolio is in a
state where the same plan is denied in one cloud and allowed in another.

The epic is called "one guard, three consumers". One guard is real and delivered. Three
consumers *of the same implementation* is real. **Three consumers of the same denylist, at
the same time, is not** — and the epic should say so rather than this file softening it.

## What would make it automatic

Four options, in the order I would recommend them:

1. **Automated bump pull requests (recommended).** Dependabot's `github-actions` ecosystem
   already watches `uses:` pins and opens a bump PR per repository on a new release. All
   three repositories have auto-merge on green. A denial would then reach all three with no
   human editing a version string — the pin stays immutable, which is the property all
   three deliberately chose, and the manual step becomes machine work rather than
   disappearing into someone's memory. It does not touch `config/cost-guard-action.txt`,
   so each repository would need its contract check taught to accept a bump that moves both
   together, or the pin file folded into the workflows.
2. **A staleness check in each consumer.** A scheduled job comparing the pinned ref against
   the latest release, failing or warning when behind. This does not make propagation
   automatic; it makes non-propagation **loud**, which fixes the dangerous half. Cheapest
   of the four, and it is the one I would ship first regardless of the others, because it
   converts a silent gap into a visible one.
3. **Pin `@v1`.** Propagation becomes immediate and free. It is also precisely what the
   three consumer packets rejected, for a good reason: what runs in their CI could then
   change with no commit in their repository. Reversing that should be an explicit
   portfolio decision about who is trusted to change what is denied, not a convenience fix.
4. **A dispatch from this repository on release** that opens the bump PR in all three.
   Equivalent in effect to option 1 but hand-built, and it needs a cross-repository token.
   Worth it only if Dependabot cannot be made to fit.

**Recommendation: 2 now, 1 next.** Together they preserve the immutable pin and remove the
silence, which is the actual defect — the delay is tolerable, the invisibility is not.
