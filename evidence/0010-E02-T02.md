# 0010-E02-T02 — The guard must survive a real plan

The empty-input check tested emptiness by deleting every whitespace character from the plan
and asking whether anything was left. Bash rebuilds the entire string to do that. The
replacement asks whether the plan contains one non-whitespace character, which is the same
question and is flat in the size of the input.

**A correction to the packet's premise, which changes the version recommendation.** The
packet says the defect is released as `v1.0.0`. The current release is `v1.0.1` — T05 cut it
to carry the Cloud NAT denial — and all three consumers were bumped to it in that packet.
The defective line is unchanged in every released version:

```
v1.0.0: 1 occurrence(s) of the rewrite
v1.0.1: 1 occurrence(s) of the rewrite
v1:     1 occurrence(s) of the rewrite
```

So the fix should be released as **`v1.0.2`**, not `v1.0.1`, and all three consumers are
affected *today* at the version they are actually pinned to.

## 1. The current implementation, timed

The suspect line in isolation, on whitespace-heavy plan JSON:

| Bytes | `[[ -z "${s//[[:space:]]/}" ]]` |
|---|---|
| 5,890 | 1.20 s |
| 11,770 | 7.05 s |
| 23,530 | 45.16 s |

Roughly six times the cost for twice the input — far worse than linear, and already past the
packet's reported "over 45 seconds" at half the reported size. Against the real 51,643-byte
plan the released guard **did not reach a verdict at all**: killed at 120 s in one run, and
a second run with a 900-second ceiling was still going when this file was written.

That is the shape of the CI symptom the packet describes. It is not a failure. It is a job
sitting at no output until the runner's timeout, which reads as a stalled runner rather than
as a guard defect — and bills for the wait.

## 2. The fixed implementation, same plans

```
plan-large-clean     exit 0  0.12s  (51643 bytes)
plan-large-denied    exit 1  0.02s  (53652 bytes)
    Denied resource: aws_nat_gateway.egress (NAT Gateway): ~$32/mo
```

The same line, measured the same way as above: 0.002 s at 5.9 KB and 0.004 s at 415 KB.
Flat, across two orders of magnitude.

**The check is not weakened, which the Boundary was explicit about.** "Empty or
whitespace-only" and "contains no non-whitespace character" are the same predicate. Only the
arithmetic changed:

```
empty file:            exit 2
whitespace-only:       exit 2
single newline:        exit 2
single space:          exit 2
single tab:            exit 2
```

## 3. The fixtures are real, and that mattered

`tests/fixtures/plan-large-clean.json` (51,643 bytes) and `plan-large-denied.json` (53,652
bytes) are `tofu show -json` output from OpenTofu 1.12.5 with the real `hashicorp/aws`
6.56.0 provider — four CloudFront distributions with different origins, price classes and
geo restrictions, three security groups, three S3 buckets, three CloudWatch log groups, and
in the denied fixture one NAT gateway.

The packet said not to synthesize by repeating a string, and that instruction earned its
place. My first attempt at reproducing the hang used base64 padding and showed **no slowdown
at all** — 32 KB in under 0.01 s — because base64 contains no whitespace and the pathology
is driven by the matches. A repetition-built fixture could easily have had the same
property, "proved" the guard fine, and closed this packet on a false negative.

The denied entry sits at index 7 of 14 in its plan, so finding it means reading through the
whole thing rather than stopping at the first resource.

**No cloud call was made and nothing was applied.** The configuration uses dummy static
credentials with `skip_credentials_validation`, `skip_requesting_account_id`,
`skip_metadata_api_check` and `skip_region_validation`; a create-only plan with no data
sources and no prior state contacts no AWS API. The scratch stack lives outside the
repository and only its rendered JSON was committed.

## 4. The size test, and that it fails against the released guard

`scripts/test-plan-size.sh` has two halves because either alone is weak:

- **Dynamic** — the real ≥50 KB fixtures must reach the *correct verdict* within five
  seconds. Catches slowness whatever causes it, including causes nobody predicted.
- **Static** — `${plan_input//…}` must not appear in the guard. Deterministic, cannot flake
  on a loaded runner, and names the specific defect.

It also asserts the fixtures are **still at least 50 KB**. Without that, the whole file can
be silently defanged by swapping in a small fixture: every other assertion would still pass
and the suite would go back to proving nothing about size. That is the same failure this
packet exists to fix, one level up.

Run against the released implementation — a `git archive` of `HEAD` with only the new test
and fixtures added:

```
Dynamic: a realistically-sized plan, verdict and time
FAIL  a large clean plan: no verdict within 5s on a 51643-byte plan.
      A guard that cannot finish is a guarded pipeline that hangs.
FAIL  a large denied plan: no verdict within 5s on a 53652-byte plan.
      A guard that cannot finish is a guarded pipeline that hangs.

Static: the whole-input string rewrite cannot return
FAIL  the guard rewrites the whole plan string in bash:
33:if [[ -z "${plan_input//[[:space:]]/}" ]]; then

The guard does not survive a realistically-sized plan.
exit: 1
```

Both halves fail against the old implementation and pass against the new one. It is
permanently held down by a mutation in `scripts/test-suite-can-fail.sh`, which restores the
quadratic line in a throwaway copy and requires the size test to go red:

```
PASS  the suite passes unmutated
PASS  aws_nat_gateway is removed from the denylist, and the suite failed
PASS  the empty-input path is softened to exit 0, and the suite failed
PASS  the quadratic empty-input check is restored, and test-plan-size.sh failed
PASS  the guard is given a network call, and test-no-network.sh failed
PASS  an unknown lookup is reported as current, and test-freshness.sh failed
```

## 5. The exit contract, unchanged

```
scripts/test-cost-guard.sh        exit 0
scripts/test-suite-can-fail.sh    exit 0
scripts/test-plan-size.sh         exit 0
scripts/test-freshness.sh         exit 0
scripts/test-no-network.sh        exit 0
scripts/demo-consumer.sh          exit 0
```

`test-cost-guard.sh` covers the same seven inputs it did before, unchanged: 1 for each
denied create, 0 for a clean plan, 2 for errored, unrecognizable and empty.

**Why the large fixtures are not in `test-cost-guard.sh`.** That suite has no timeouts, and
`test-suite-can-fail.sh` runs suites expecting them to fail. A slow implementation there
would hang the meta-test rather than fail it, so the size assertions live in
`test-plan-size.sh`, which bounds every run with `timeout`. A test that hangs instead of
failing is the same defect in miniature.

## The same shape elsewhere, as the Notes asked

Two more whole-string rewrites exist in this repository, both in `scripts/freshness.sh`:

```
scripts/freshness.sh:30:if [[ -z "${pin//[[:space:]]/}" ]]; then
scripts/freshness.sh:43:if [[ -z "${repo//[[:space:]]/}" || -z "${ref//[[:space:]]/}" ]]; then
```

**Not currently a problem, and deliberately not changed** — the Boundary says not to touch
the freshness action. They operate on a pin string like `martcoca/cost-guard@v1.0.1`, tens
of bytes, where the cost is unmeasurable. They are reported because the Notes asked for the
shape rather than the symptom, and because the guard's line was also harmless until its
input grew. If freshness ever takes a larger input, these are already wrong.

Everything else in the guard hands the whole input to `jq`, which streams it. The one
remaining whole-input operation is `plan_input=$(cat -- "$plan_file")`, which is linear and
is **required**: the guard accepts `/dev/stdin`, and stdin cannot be read a second time, so
the plan must be buffered once rather than re-read for each of the three `jq` passes.

## What this should be released as, and what the consumers must do

**`v1.0.2`.** A patch: a defect fix with no change to the exit contract, the denylist, the
action's inputs and outputs, or the freshness action. Nothing a consumer depends on changes
shape. `v1` should move to it.

**I did not tag it.** Tagging is publication and is not mine; the Boundary said so and I am
not treating this packet as authority to do it.

To pick it up, per T01's evidence in `0010-E02-T01` and T05's before it, each consumer needs
a pin bump — `config/cost-guard-action.txt` plus every `uses:` in its workflows, and for
`platform-azure` also the `ref:` on its release checkout. Three pull requests. Propagation is
still not automatic, and this fix is a good argument for the staleness signal from T01 being
adopted: a consumer left on `v1.0.1` does not get a warning that it is running a guard that
hangs, it simply hangs.

**This one deserves more than the usual bump.** The other denials propagate late and the cost
is a gap in coverage. This one propagates late and the cost is CI jobs that hang until
timeout, on three repositories, billed by the minute. If any consumer plans a stack that has
grown past roughly 20 KB of plan JSON, it is already paying for this.

## What I could not verify

- **The exact completion time of the released implementation on the 51 KB plan.** Two runs
  were killed — one at 120 s, one still running past 900 s when this was written. The
  honest statement is "no verdict in fifteen minutes", not a number. Extrapolating the
  measured curve puts it in the several-minutes-to-hours range, but I did not let it finish
  and will not claim a figure I did not observe.
- **That 47 KB is the threshold**, or that any particular real consumer stack is over it.
  The packet reports a 47 KB plan from real infrastructure; I did not reproduce that
  specific plan. What I measured is that 23.5 KB already costs 45 s, so the practical
  threshold is well below 47 KB.
- **Behaviour under other bash versions.** Measured on GNU bash 3.2.57 (macOS) locally; CI
  runs bash 5.x on Ubuntu, where the constant factor differs. The fix is flat on both, and
  the CI job is what confirms the Linux side.
- **The CI runs, at the time of writing.** Whoever reads this after the pull request has
  them.
